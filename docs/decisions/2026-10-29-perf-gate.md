# 决策：引擎层性能门禁 —— 12 个用例、p50×3 预算、1.3× 回归护栏

- **日期**：2026-10-29
- **状态**：✅ 已实施（`backend/bench/bench_engine.cpp` + `baseline.json` + `budgets.json` +
  `ctest perf_gate`，opt-in）
- **标签**：`#性能 #门禁 #后端 #引擎 #测试`
- **上游决策**：[后端持有数据与计算（B 方案）](2026-10-17-backend-owns-compute.md)（计算权威在后端，
  所以"后端变慢了"就是产品变慢了）、[兜底原则（最大余量）](2026-10-15-max-headroom-principle.md)
  （宁可在最贵的一档留余量，也不要在平均意义上省）

## 核心表述

> 「变慢了」必须是一个能复现的数字，而不是一次会议上的感觉。
> 12 个用例钉住「6×10 万行这张表算一遍」和「512² 矩乘/LU 这一档」，p50 超首测 3 倍或
> 超基线 1.3 倍就红；引擎代码一行没改，先有尺子再谈优化。

## 背景（为什么现在补这条）

在途的「结果预览 / 稠密帧」lane 和还在讨论的前端统计搬迁，都会碰到同一条路径：
公式 + 数据 → 结果。过去三个月改这条路径靠的是「跑一下看看卡不卡」，于是：

- 没有数字，回归只能靠用户先感觉到——上一次发现评测变慢，是柱状图拖拽掉帧之后回查出来的；
- 没有口径，两个人都说"快"，但一个在量 HTTP 往返、一个在量引擎本身，谁也没错，谁也说服不了谁；
- 没有门槛，「这次先合，下次优化」的概率远大于「这次先测」。

B 方案把计算放在后端，这条路径的每一毫秒都直接落在用户等待上。所以在动它之前，
先给引擎层立一把可执行的尺子。

## 决策内容

### 1. 为什么是这 12 个用例

| 用例 | 类 | 尺寸 | 代表什么 |
|---|---|---|---|
| `elem.add` | 逐元素 | 6×100000 | 最基本的一条：内存带宽与向量化 |
| `elem.sqrt` | 逐元素 | 6×100000 | 超越函数（sqrt 走 SIMD 慢路径） |
| `elem.branch` | 逐元素 | 6×100000 | 分支/掩码（`IF` 两条手臂都要走） |
| `elem.aggregate` | 逐元素 | 6×100000 | 先归约再广播（`MEAN` 走全列） |
| `elem.window` | 逐元素 | 6×100000 | 滑动窗口（边缘钳制的那个分支） |
| `elem.k5` | 逐元素 | 6×100000 | 一张卡 5 条公式：tokenize/列映射/解析/编译各做 5 次 |
| `mx.transpose` | 矩阵 | 6×100000 | 转置：跨步拷贝，宽表转成 10 万×6 |
| `mx.mixed` | 混合 | 6×100000 | `A * TRANSPOSE(A)`：内维 10 万、结果只有 6×6 |
| `mx.matmul` | 方阵 | 512×512 | O(n³) 的基准项 |
| `mx.inv` | 方阵 | 512×512 | LU + 三角求逆（比 matmul 贵一个常数档） |
| `mx.det` | 方阵 | 512×512 | 只要 LU，用来分辨「LU 慢」还是「求逆慢」 |
| `mx.solve` | 方阵 | 512×512 | LU + 512 个右端项，`SOLVE` 的真实形态 |

选型依据三条：

- **尺寸来自目标数据，不是拍的。** 6×100000 就是本项目要处理的那张表：6 个变量、10 万行
  （`work/demo-data.zip` 里的数据集基本都在这个量级）。512² 是 O(n³) 那一档的代表——
  n³ 的常数项在 512 时已经压过噪声，再大就变成"测机器"了。
- **一个用例只回答一个问题。** `mx.det` 和 `mx.inv` 都是 LU 家族，但拆开才知道贵在分解还是
  求逆；`elem.k5` 单独把「重复编译」的成本隔离出来（真实路径每次 `evaluate` 都重做
  tokenize/解析/编译，不缓存）。
- **先引擎层，HTTP 层留到下一步。** 引擎层没有端口、线程、序列化、socket 超时这些变量，
  数字是确定的、可复跑的；HTTP 层的回归要等这层稳定之后再叠——否则分不清是公式变慢还是
  传输变慢。这也是「一个门禁只管一件事」的直接应用。

### 2. 阈值怎么来的

1. **第一遍不定卡**：`DC_RUN_BENCH=1 ./backend/build/dc_bench --update-baseline`，
   把每例的 p50/p95 写进 `backend/bench/baseline.json`（附 `machine` / `git` / `taken_at`）。
2. **预算**：`max_ms = 首测 p50 × 3`，向上取到 0.1 ms，写进 `backend/bench/budgets.json`，
   并注明 `generated_from`（基线文件、git、时间、机器）。**没有一个数字是手填的。**
   3 倍不是拍脑袋：引擎层的正常波动（频率、缓存、分配器）实测在 ±10% 以内；
   3 倍意味着只有真正的结构性变慢才会撞线，同时不会把「今天机器有点热」当成回归。
3. **回归护栏 1.3×**：每次带卡跑都与基线比 p50。绝对阈值管「太慢」，相对阈值管
   「比上次慢」——后者才是日常最常发生的事。用相对值兜机器噪声：换一台机器绝对数会变，
   但同一台机器上的比值可复现。

判红条件（任一）：某例 p50 或 p95 超 `max_ms`；或 p50 超基线 `regression_ratio`（1.3×）。
红了**不做当场优化**：贴数字、等裁决，先把「是噪声还是回归」问清楚。

### 3. 口径（比"测了多少次"更重要的部分）

- **不报平均值。** 平均值会被一次调度抖动整段拖歪；报 p50（典型）与 p95（尾巴）。
- **p95 用线性插值**，不用最近秩的最大值：15 个样本时最近秩的 p95 就是最大值，
  一次抖动会把整个指标变成「最坏那一趟」，门禁会假红。
- **测量前把进程钉在当前 CPU 上**（`sched_setaffinity`，尽力而为）。实测：不钉时短用例
  （0.19 ms 的 `elem.add`）在核间迁移下会跳 21%，正好压着 1.3× 护栏；钉住后稳定在 1% 内。
- **输入数据不许带 NaN/Inf/denormal**：这些值会让浮点路径走进慢速通道，把计时拖歪。
  512² 的 B/C 做成对角占优——只影响数值良态性，不改变 LU 的运算量。

### 4. 扩展方式（框架不改）

加一个算法 = 两处：① `bench_engine.cpp` 的 `cases()` 里加一行（name / 是否矩阵 / 公式 / 变量）；
② `budgets.json` 的 `cases` 里加同名一条 `max_ms`。只有需要**新数据形状**时才改 `buildData()`。

### 5. 采用 / 否决

**采用**：自包含 C++17 + `<chrono>`，链接 `dc_core`，直接调 `ExprEngine::evaluate` /
`evaluateMatrix`；opt-in（未设 `DC_RUN_BENCH=1` 时 exit 101，ctest 记 Not Run）。

**否决**：

| 方案 | 否决理由 |
|---|---|
| 引 Google Benchmark / Catch2 等微基准框架 | 为一个 12 行的表引入第三方依赖与构建改动，收益不抵维护面；`<chrono>` 足够 |
| 直接压 HTTP `/api/nodes` | 混入端口、线程、JSON 序列化、socket 超时；分不清公式慢还是传输慢（这正是要拆开的东西） |
| 绝对阈值（"每例 < 10ms"） | 换机器就失效；本仓库的机器不止一台，绝对数只会制造误报 |
| 报平均值 | 被单次抖动拖歪，看不见尾巴 |
| 把门禁挂进 CI 常跑 | 性能数字依赖机器的当前状态，CI runner 上只会周周假红；先保持 opt-in，CI 只保留「编译 + 现有测试」 |

## 边界

- 只管**引擎层**：HTTP、节点注册表、缓存命中、冷启动都不在覆盖范围内。
- 计时是**单线程**的（Eigen 未开 OpenMP）：多线程路径的收益/退化在这把尺子上看不见。
- 基线**属于一台机器**：`baseline.json` 附了 `machine`；在别的机器上跑会打印提示，
  预算仍按本机判，回归比对仅供参考。换机器要重新 `--update-baseline`。
- 进程被钉在 CPU 上，读数是「这颗核上」的——这是为了可复现，不是为了最漂亮。

## 与会改变这些决定的信号

- **HTTP 层出现回归**（用户感到慢、引擎层却全绿）→ 这说明需要第二条门禁覆盖传输与序列化。
- **数据形状变化**（目标数据集变成 100 万行，或变量数超过 10）→ 用例尺寸要跟着改，
  基线作废，重新取。
- **开始用多线程 / 开 OpenMP** → 单线程读数的说服力下降，要把「并发下的 p95」加进来。
- **门禁开始频繁假红** → 说明阈值或口径要改（先怀疑 3× 与 1.3× 的取舍，再怀疑机器），
  这本身就是一次需要新决策的变更。
- **有了固定的 CI 性能机** → opt-in 可以升级为常跑，前提是那台机器的噪声特征先被量过。
