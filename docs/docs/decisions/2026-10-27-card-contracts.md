# 决策：函数卡的三个契约（列数 · 参数归属 · 单列端口）

- **日期**：2026-10-27
- **状态**：🔒 已定稿并实施
- **标签**：`#架构 #函数卡 #端口语义 #契约`
- **配套文档**：[卡片数据结构 v2](./2026-10-26-card-schema-v2.md)、[端口语义规格 v1](../architecture/port-semantics-v1.md)
- **背景**：实现 v2 的过程中，三处「两种说法都说得通」的地方必须当场定死，否则代码会各自长出
  一套解释——本仓库历史上最贵的一类 bug（三份互不相同的端口定义）就是这么来的。

## 一、列数契约：命名输出列即锁宽度

**问题**：用户在输出区给列起了名字，之后若上游宽度变了，位置映射会把用户的名字挪到别的列上。
**曾考虑的方案**：记录上游列头快照做指纹比对，出现差异就警告。
**否决理由**：线性代数链路（转置、SVD、切片）列数/列宽本来就常变，指纹的误报率与其实现复杂度
不成比例；而且它猜的是「用户在意什么」，猜错了就是无休止的黄色警告。
**采用**：显式契约 `params.columnContract = { outputId, columns }`。第一次命名某一列时锁定当时
的列数；此后宽度漂移由后端以 `columnContractViolation{expected, actual}` **断流**（清空旧结果，
下游继承 `upstreamError`），卡片底部提示条给出两条出路：「扩展契约到 M 列」「解除锁定」。
**边界**：契约是参数（数据），不是形状猜测；K（输出个数）仍由签名定；行数不参与契约
（表达式按列名取值，行数不是映射）。

## 二、参数归属：参数属于签名，不属于卡片

**问题**：输出列名放哪？曾计划 `outputs[].columnNames` 与表达式 `name` 并存。
**否决理由**：同一能力两个入口，必然长期漂移（这正是「双接口同功能」禁令的由来）。
**采用**：列名只存在于签名自己的参数里（`params.formulas[].name`）；输出区顶端的重命名只是它的
另一个**编辑面**，不是第二个数据源。`FunctionCardModel.params` 因而改为开放结构：某个签名有没有
参数、参数是什么形状，由签名决定——给每个签名强塞一个空 `formulas: []` 等于把谎话写进数据。
**推论**：卡片参数区必须按签名渲染（有 `formulas` 才是编辑器，没有就直述「输入由端口决定」）。

## 三、单列端口：`mode` 必须有语义

**问题**：`PortBinding.mode` 从 v1 就存在，但从未被读取——标了 `cell` 的端口实际绑的是整张表。
**采用**：`mode: "cell"` + `columnIndex` 只绑该列（越界 ⇒ `unknownColumn`）；`"matrix"` 绑整表。
**判据**：签名可以声明「一个列」或「一张表」，这不是装饰差别——回归卡的两个端口各要一列，
把整表塞进去再让它「随便挑一列」就是把错误藏进成功路径。
**推论**：`gatherInputs` 返回每个端口的列区间（`PortSlice`），多输入签名按端口取列，
不再自己算偏移。

## 与会改变这些决定的信号

- 需要**逐列异构**的上游（同一输出的不同列来自不同来源）→ 列数契约要升级为列标识契约。
- 出现**参数需要前端渲染表单**的签名（如置信区间、窗口大小）→ `/api/signatures` 必须宣告参数
  元数据，卡片参数区随之从「陈述」变成「表单」。
- 出现 **K > 1** 的签名 → 前端需要「输出选择器」（当前每张卡只有一个显示缓存），
  这会改动 `FunctionCardModel.displayMatrixId` 的形状。
