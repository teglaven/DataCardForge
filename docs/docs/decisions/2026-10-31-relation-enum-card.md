# 决策：回归卡改名为「关系枚举」——选列变成端口绑定，列头带上 `X : Y`

- **日期**：2026-10-31
- **状态**：✅ 已实施（前端；后端零改动）
- **标签**：`#前端 #函数卡 #关系枚举 #端口绑定 #表格`
- **上游决策**：[函数卡的三个契约](./2026-10-27-card-contracts.md)（单列端口 = 判据）、
  [卡片数据结构 v2](./2026-10-26-card-schema-v2.md)（一卡一节点）、
  [端口级连线](./2026-10-28-port-level-connections.md)（连线只认 `portId`）

## 背景：三件事同时被报告

1. **名字承诺了选择，实现却是硬编码**。菜单写「新建回归卡…」，实际只能取"点中的列 + 右边一列"，
   点到最后一列直接禁用（`cols - column < 2`）。任何"有意义的配对不是相邻两列"的表都用不了它。
2. **列名是密码**。输出列标签是裸 slug：`slope` / `intercept` / `r` / `r2` / `n`。
   前四个还能猜，`n` 完全看不出是什么（它是**真正参与拟合的行数**，不是表的行数）。
3. **横向滚动时表头与表体不同步**。列数超出卡片宽度、向右拖动时，标题行与数据明显错位。

## 决策

### 一、显示名改「关系枚举」，签名 id 不动

`builtin:linear-regression` 的 id、端口（`x`/`y`，各一列）、输出（`fit`，1×5）、求值语义
（`compute: "auto"`）**全部不变**。改的只有人看的部分：菜单、卡片标题、badge、i18n key
（`menu.newRegression` → `menu.newRelationEnum`）。

> id 是发布后的稳定身份（[port-semantics-v1](../architecture/port-semantics-v1.md:17) 「发布后永不改」）。
> 语义没变就不该换 id；换了 id 等于多一个签名，而能力并没有多一个。

### 二、选列 = 端口绑定，不是参数

卡片输入区里每一个 `mode: "cell"` 的端口各带一个**列下拉**（列出该端口所绑矩阵的全部列，
按列序）。选完立刻重算。实现是 store 的新动作：

```
setPortColumn(cardId, portId, columnIndex)
  → 改 inputs[port].target.columnIndex（越界 / 非 cell 端口 = no-op）
  → 一次 PATCH（同一个 node、同一条边；params 仍然为空）
```

**为什么不是 `params`**：参数属于签名（[2026-10-27 契约](./2026-10-27-card-contracts.md:22)），
且"参数不产生也不删边"；而"哪个列喂哪个端口"是数据流，是绑定。把它做成参数会让卡片长得像
表单、数据流长得像配置，两条路以后必然分叉。

**菜单随之取消"剩余两列"限制**：只要表 ≥ 2 列就能建；点到最后一列时用**前一列**当默认 `y`。
默认只是起点，两个端口随后都能改。

否决"多选列、一次枚举所有列对"：那是**新签名**（一卡一节点、K 与形状由签名定），需要后端 C++
与 `card_fixtures`，不在本轮。见文末信号。

### 三、列头承载关系：`<x> : <y> · 统计量`

输出表的每个列头 = 这一对列 + 这个统计量的可读名：

| 稳定 slug（后端发） | 显示（i18n） |
|---|---|
| `slope` | 斜率 |
| `intercept` | 截距 |
| `r` | 相关系数 r |
| `r2` | 决定系数 R² |
| `n` | 样本数 n |

**为什么写在列轴上**：传输层只有列标签通道（`Matrix` 只带列 `annotation`，没有行标签），
"这个数描述的是哪两列"只能挂在列轴上；将来若做"一行一对"，行身份仍然没有通道（`builtin:summary`
是靠"行 i ⇔ 目录第 i 项 + 夹具逐值守卫"顶住的，一回事）。所以本轮先在列轴上把关系说清楚。

实现是 `VirtualTable` 的可选 `columnLabel` 覆盖（卡片传入），数据层与协议零改动；
后端继续只发稳定 slug，**不写用户句子**（[backend-protocol-v1](../architecture/backend-protocol-v1.md) 结构化错误一节的口径）。

### 四、表格横向滚动：行不再二次平移

根因：`.vtable__viewport` 本身是原生滚动容器（`overflow: auto`，canvas 带显式宽度），浏览器已经
按 `scrollLeft` 平移了内容；而行元素又各自加了 `translateX(-scrollLeft)`，于是表体被平移两次、
表头（在滚动容器之外，必须自己跟）只平移一次——列越多越明显，短表根本看不出。
修法：**删掉行上的 transform**，表头继续用 `scrollLeft` 跟随；行号列靠 `position: sticky; left: 0`
保持可见。`web/tests/VirtualTable.dom.test.tsx` 钉住"表头恰好平移一次、行一次都不平移"。

## 后果

- 这张卡第一次有了"选择"：任意两列；不再需要"相邻"这个产品隐式约定。
- 列头变长（`A : B · 决定系数 R²`），卡片更依赖横向滚动——所以第四条必须先修，否则是
  "把不可用的表变得更不可用"。
- 菜单语义变了：末列从"禁用"变成"与前一列配对"。测试同步（`InfiniteCanvas.dom.test`）。
- 后端、协议、夹具、性能门禁均无改动；`ctest 8/8` 不变。

## 验证

- `npx vitest run`：**567 passed | 14 skipped**（新增 4：VirtualTable 2、store `setPortColumn` 1、
  末列配对 1）

## 与会改变这些决定的信号

- **真的要做"暴力枚举"（一次算尽选中列的所有列对）** → 需要新签名，形如
  `builtin:relation-matrix`：一个矩阵输入、输出表 **行 = 列对、列 = 5 个统计量**（或反过来），
  `compute: "explicit"` 惰性求值、复用 DCM2 的分页预览。届时"`X : Y · 统计量`"的命名规则直接沿用；
  行身份要么沿用目录序 + 夹具，要么先给传输层加行标签通道——后者是协议改动，需要单独决策。
- **出现第三类"必须自选输入列"的签名** → 列下拉应抽成通用控件（当前只有 cell 端口渲染它）。
- **有人要求按列头排序 / 导出配对表** → 那是"表视图"的能力，不该塞进这张卡。
