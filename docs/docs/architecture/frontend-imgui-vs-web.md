## 两条路线总览

### A. ImGui（+ ImPlot + GLFW）

- **强项**：性能（大数据表 + 高频重绘 + 零拷贝矩阵）、连线/自由绘制（ImDrawList）、C++ 原生、插件可分层
- **弱项**：矢量导出（ImPlot 明确无导出、非出版级）、SVG WYSIWYG 编辑（几乎要自建编辑器）、中文 IME 麻烦、无官方插件系统

### B. Web（Tauri / 纯 Web）

- **强项**：SVG 原生（矢量导出免费）、WebView 嵌入成熟、HTML/CSS 生态、IME 好、WYSIWYG 类功能是天然强项
- **弱项**：性能上限低于原生（大数据表/高频需额外优化）、包体（Tauri 小 / Electron 大）

## 关键权衡表

| 需求 | ImGui | Web |
|------|:--:|:--:|
| 大数据表 + 高频图表 | ✅ 强 | ⚠️ 需优化 |
| 窗口间连线 | ✅ 强 | 🟡 可行 |
| 矢量导出（出版级） | ❌ 弱（需自建导出管线） | ✅ 原生 |
| SVG / WYSIWYG 编辑 | ❌ 极难 | ✅ 原生 |
| 中文 IME | ⚠️ 需专门处理 | ✅ 免费 |
| 插件开发 | 🟡 中（无生态设施） | 🟡 中（npm 但隔离弱） |

## 已论证的关键结论（勿重复讨论）

1. **连线从属原则**下，WebView 若作为卡片嵌入 ImGui，**走子窗口模式即可**，无需 OSR（见 [连线从属原则](../decisions/2026-08-07-connection-subordination.md)）
2. **若"矢量导出 + SVG 编辑"被证实为高频需求** → Web 权重应大幅上调（这是 ImGui 最大相对劣势）
3. ImPlot 生态：健康但偏小，v1.1 处于 API 重写期（见 [ImPlot v1.1 API 大改](../lessons/implot-v1.1-api.md)）；ImGui 生态庞大且极其健康
4. 导出管线应**与交互显示分离**（交互用 ImGui/ImPlot，导出用 matplotlib 桥或数据驱动 SVG），无论选哪条路都成立
