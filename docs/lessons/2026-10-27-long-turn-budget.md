- **日期**：2026-10-27
- **标签**：`#踩坑 #成本 #长上下文 #会话治理`
- **结论先说**：不是模型贵，是**回合太长 + 工具输出回灌**。同一个病在当晚出现了两次：一次在 qwen3.8-max（190.1M tokens），一次在我自己的收尾回合（171.5M）。

## 规则（可直接抄进任务书）

1. **一个回合只做一件事**；每片做完就提交 + 写日志，然后开新回合。回合边界是唯一可靠的上下文重置点。
2. **侦察走 `subagent`，只读、并行**；**禁止 `subagent_fork`**——它把整段对话复制进子代理，正好是被监督的那部分。
   本地只读侦察用 profile 里的 `qwen3827b`（127.0.0.1:8081，27B GGUF），不要占用 agent 正在用的端点。
3. **单回合预算**：> 8M tokens 或 > 0.8 元 → 黄灯；> 20M 或 > 1.5 元 → 停。
4. **15 分钟无提交 = 在做侦察；30 分钟无提交 = 停**（前提：调用是密的；讨论回合不算）。
5. **压缩（compaction）即结算点**：先落盘（提交 + 日志 + 决策记录），再压缩；不要在压缩后继续用半截上下文救火。
6. **硬刹车只在回合边界上生效**；无人值守时段唯一可靠的闸是 provider 额度，余额按"一晚 10–15 元"留（账本实证）。

```
1. git status --short 与 git log -1 —— 原样贴出
2. 自上次提交以来：文件清单 + git diff --stat 最后一行
3. 本回合跑过的门禁各一条关键输出行；没跑写"未跑"
4. 停在哪一步（一句话），下一步最小可交付动作（一句话，具体到文件）
5. 结论三选一：收窄继续 / 压缩重启 / 交人决策
```

## 三条被否掉的方案（写下来防止下次又走回头路）

1. **问模型"执行是否有问题"** → 它看不见自己的预算、读的正是让它打转的上下文、训练偏好是"报进展"，只会得到廉价回答。改成"列证据，人来判"。
2. **把"今天没提交"当红灯** → 第一版在 21:31 判 RED，而那时整天在讨论、会话是空闲的。空闲（无结算 > 30 分钟）与卡死必须分开。
3. **靠低额度当控制回路** → 它是保险丝：烧断时整个会话一起停，保护的是"能立刻充值的钱"，赔的是"充不回来的时间"。余额只负责"无人值守时最坏别亏穿"。
