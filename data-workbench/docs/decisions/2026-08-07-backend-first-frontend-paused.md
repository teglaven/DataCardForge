# 决策：后端先行，前端搁置

- **日期**：2026-08-07
- **状态**：🔄 部分取代 —— **"前端选型暂停"已被 [[2026-10-14-frontend-web-chosen|前端选型定为 Web]] 取代**（2026-10-14）；"后端优先"的优先级判断仍然有效
- **标签**：`#架构 #优先级 #前端选型`

## 背景

项目处于早期试验阶段。此前长期在讨论前端方案（ImGui / Web / Tauri），但发现：
- 大量讨论陷入"实现细节"（OSR、连线图层、插件 ABI），偏离了用户视角
- 前端能展示什么，受限于**后端能算什么**——后端未定型时，前端选型是空中楼阁
- 矢量导出、3D 等"可能的需求"尚不明确，过早选型风险高

## 决策内容

1. **后端优先实现**：
   - [ ] Eigen 集成：线性代数（列运算、矩阵乘法、特征值等）
   - [ ] 逐元素公式计算（SUM / AVG / MIN / MAX / IF 等）
2. **视图层暂用现有 Qt Widgets 凑合**，不投入改造
3. **前端选型（ImGui / Web）暂停**，待后端核心落地后再综合评估

## 原因

- 后端（`core/` + `loaders/` + Eigen 计算）是**跨前端可复用的资产**，先做不浪费
- 前端最终形态取决于后端能力（例如：是否需要逐元素编辑、公式卡如何呈现）
- 避免在"未来可能换掉的技术"上重复投入

## 后续（2026-10-14 追记）

本决策有两条内容，命运不同：

1. **"后端优先"** —— 依然成立。Eigen 与逐元素公式计算仍未落地，且 Web 侧还需决定走 WASM 还是 TS 实现。
2. **"前端选型暂停"** —— **已废止**。2026-10-14 重新评估后前端定为 Web，并直接给出了实现
   （`web/`，React + Vite + TypeScript + ECharts）。当时担心的"性能"被实测证伪，而
   当时视作"可能需求"的矢量导出被确认为硬需求。

> 方法论上的收获：本条决策里"待需求明确后再选型"的思路是对的，但**"矢量导出是可能需求"这个前提错了**——
> 它其实是终点需求。教训是**区分"用户最终要交付什么"和"中间过程需要什么"**，前者不能延后决策。

## 未来影响

- 后端落地后，重新评估 [[frontend-imgui-vs-web|前端选型]]
- 若矢量导出、3D、SVG 编辑等需求被证实高频 → 前端选型权重将向 Web 倾斜
